# Risks & Open Questions

This is a living document. Each item should be checked off (with the actual measured result, not just "done") once its corresponding Phase 0 spike or later-phase decision resolves it. Nothing here should block writing code — Phase 0 exists specifically to convert these from assumptions into facts before the rest of the roadmap depends on them.

## Unresolved — gated by Phase 0 spikes

- [ ] **LLM speed and model choice are unvalidated on the actual hardware.** The July-2026 research pick is `qwen3.5:4b` (fits the 4GB VRAM fully — should be markedly faster than any partial-offload 7B) with `gemma4:e4b` as grammar alternate, but no number has been measured on this exact machine (i5-11400H, RTX 3050 4GB, 16GB RAM effectively at 2400MHz due to mismatched DIMMs). **Action**: Phase 0 spike #6 ([06-ROADMAP.md](06-ROADMAP.md)) runs the three-model bake-off (tok/s + hand-scored grammar eval + prefix-cache TTFT delta) before the default is locked and before any UX pacing (debounce timing, auto-suggest default) is treated as final.
- [ ] **`qwen3.5:4b` / `gemma4:e4b` exact tags need verifying on Ollama's official library at Phase 0** — the small-model landscape churns fast (this project has already retired one default). If a tag has moved, pick the nearest current equivalent by the same criteria: fits 4GB VRAM fully, instruction-following-first, per [11-AI-INTELLIGENCE.md](11-AI-INTELLIGENCE.md) §1. `local_model_name` stays a runtime setting precisely for this reason.
- [ ] **Tauri + PyInstaller sidecar packaging** is a known source of "works in dev, breaks in the packaged build" bugs. Research surfaced three *specific* gotchas, not just a generic warning, from real Tauri+FastAPI+PyInstaller repos (`dieharders/example-tauri-python-server-sidecar`, `AlanSynn/vue-tauri-fastapi-sidecar-template`, and the aiechoes.substack.com writeup):
  1. **`process.kill()` on the Rust side does not actually stop a one-file PyInstaller executable** — Tauri only holds the PID of the PyInstaller bootloader process, not the real Python child process underneath it, so a naive "kill the sidecar on window close" leaves an orphaned process running. **Action**: implement an explicit shutdown command (e.g. a stdin signal or a `/shutdown` endpoint the Rust shell calls before killing the process) rather than relying on OS-level process termination; alternatively, package with PyInstaller's `--onedir` mode instead of `--onefile`, which doesn't have this bootloader-wrapping problem. Verify whichever approach is chosen in Phase 0 spike #1.
  2. **ML-adjacent Python packages can fail silently under PyInstaller** unless the `.spec` file explicitly uses `collect_dynamic_libs()`/`collect_data_files()`/`hiddenimports` for them — a package importing cleanly in dev can crash on load in the packaged build with no obvious error. **Action**: build the sidecar's PyInstaller `.spec` incrementally in Phase 0, testing each new dependency (SQLAlchemy, litellm, etc.) as it's added, rather than writing one spec file at the end and debugging failures in bulk.
  3. **Windows requires `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` set before any imports**, or the packaged executable can crash on any output containing non-ASCII characters (a real risk for a story-writing app with international character names/text). **Action**: set both env vars at the very top of the sidecar's entry point, before any other import.
  4. Sidecar binaries must be named exactly `<name>-<target-triple>` or Tauri silently fails to find them at build time — already known generically, reinforced here with a concrete naming-convention reminder.
- [ ] **WeasyPrint's GTK/Pango dependency isn't natively pip-installable on Windows**, and bundling it is explicitly outside the WeasyPrint maintainers' supported scope. **Action**: Phase 0 spike #3 is a pass/fail test of DLL-bundling; `ReportLab` (pure-Python, no native deps) is the ready fallback if it fails.
- [ ] **`pyrage`'s Windows wheel is a single-maintainer dependency.** **Action**: Phase 0 spike #4 confirms current PyPI wheel coverage for the target Python version; AES-256-GCM + Argon2id (`cryptography` + `argon2-cffi`) is the documented fallback, since encryption itself is a hard requirement regardless of which library provides it.
- [ ] **FDX round-trip fidelity via `screenplay-tools` is unproven at scale** — it's a small, relatively young library. **Action**: verify scene numbering, dual dialogue, and title-page metadata against a real FDX-aware viewer (e.g. actual Final Draft or Highland) before trusting it beyond basic interchange; do this check in Phase 6, not just Phase 0's minimal round-trip spike.
- [ ] **Ollama's cancel-on-disconnect behavior needs empirical confirmation.** The debounce/cancel UX (see [04-LLM-INTEGRATION.md](04-LLM-INTEGRATION.md)) is only a real performance win if closing the httpx stream to Ollama actually stops its generation loop promptly, rather than just dropping the response on the frontend while Ollama keeps computing in the background. **Action**: verify directly in Phase 2 when the streaming Enhance call is first wired up; if cancellation turns out to be cosmetic-only, revisit whether auto-suggest is viable at all on this hardware.
- [ ] **Groq's free-tier model lineup churns quickly** — a single deprecation wave in June 2026 removed several models (`llama-3.1-8b-instant`, `llama-3.3-70b-versatile`, `qwen/qwen3-32b`, `llama-4-scout-17b`) in favor of newer ones. **Action**: `groq_model_name` must stay a runtime setting, never hardcoded in code; Phase 0 spike #5 and any later Groq-facing work should re-check `console.groq.com/docs/models` rather than trusting this document's specific model names as permanent.
- [ ] **Groq structured-output reliability varies by model** — `stream=True` and JSON-schema `response_format` are mutually exclusive, and strict schema compliance is only certified for the `gpt-oss` family; other models are best-effort and can emit invalid JSON. **Action**: the continuity-checker's JSON parsing must validate-and-retry defensively for any Groq model, not assume Ollama-level structured-output reliability (see [08-AI-PROVIDER-MODES.md](08-AI-PROVIDER-MODES.md)).
- [ ] **LiteLLM is a large, fast-moving dependency** — chosen because it already speaks OpenAI-compatible Ollama and Groq with zero custom mapping, but it has open bugs in its fallback/retry interaction (e.g. `BerriAI/litellm#19985`). **Action**: keep it strictly behind the project's own `ProviderClient` interface (never called directly from route handlers) so it can be swapped for a hand-rolled thin client later without touching call sites, per [08-AI-PROVIDER-MODES.md](08-AI-PROVIDER-MODES.md).
- [ ] **No known open-source project actually bundles Ollama itself as a Tauri sidecar.** A search for real-world Tauri+Ollama apps (`vanvuongngo/ollama-tauri-qwik`, `elijahmg/ollama-tauri-client`) found every one of them simply assumes Ollama is already installed and running externally, hitting its HTTP API — none spawn/manage the `ollama.exe` process themselves the way [02-ARCHITECTURE.md](02-ARCHITECTURE.md)/[04-LLM-INTEGRATION.md](04-LLM-INTEGRATION.md) currently plan to. (Bundling a *raw inference engine* as a sidecar is validated prior art — `dillondesilva/tauri-local-lm` does this with llama.cpp directly — just not Ollama specifically.) **Action**: Phase 0 spike #2 should explicitly test whether Rust-managed `ollama.exe serve` spawn/health-check/kill is reliable before committing to it; if it proves fragile, the documented fallback is either (a) detect an existing Ollama install and prompt the user to install it themselves on first run (matching the pattern every found example actually uses), or (b) bundle `llama.cpp` directly instead of Ollama, trading away Ollama's convenient model-pull/management API for the validated sidecar pattern.
- [ ] **`sqlite-vec` has a bus-factor concern.** It's the right technical choice (vectors inside the existing SQLite file, Mozilla Builders-sponsored, official PyPI Windows wheel), but it's substantially a single-maintainer project that went ~6 months quiet in 2025 (issue #226 "is this maintained?"; a community fork `vlasky/sqlite-vec` appeared) before upstream resumed in 2026 with a stated stable-v1-then-maintenance plan. **Action**: Phase 0 spike #8 validates the current wheel; mitigations if it ever stalls: the vec0 format is plain SQLite (data is never trapped), the fork exists, and at this scale a NumPy brute-force fallback over a BLOB column is a weekend replacement. Semantic layer is v1.1, so there's schedule room to react.
- [ ] **Piper TTS is GPL-3.0 (the active fork `OHF-Voice/piper1-gpl`; the original MIT `rhasspy/piper` is archived).** **Hard rule**: Piper runs as a **separate standalone process** communicating over stdin/HTTP — never imported into, linked with, or bundled inside Quillnight's own executables — keeping the GPL boundary at the process line. **Action**: revisit the isolation design in Phase 11 before implementation; if the boundary ever feels ambiguous, drop Piper and keep Web Speech only (read-aloud still works, just with system voices).
- [ ] **Rive mascot asset requires a paid export** (~$9/mo tier for one month; the editor is free to design in). **Action**: budget the one month during Phase 11, or use the documented fallback (layered-SVG mascot animated with Motion variants — same states, less fluid). The v1.0 ambient firefly has zero asset dependency either way.
- [ ] **Parakeet/`onnx-asr` + PyInstaller packaging is unproven** — onnxruntime DLL collection is the known risk area (same class of problem as the WeasyPrint/GTK item above). **Action**: Phase 0 spike #7 is a pass/fail packaging test; documented fallback is a whisper.cpp Vulkan standalone sidecar exe (no Python packaging surface at all).
- [ ] **Prefix-cache wins depend on configuration discipline.** The KV cache is per-slot: `OLLAMA_NUM_PARALLEL` > 1 interleaves requests across slots and silently evicts the cached prefix; model unload (`keep_alive` expiry) drops it too; and one volatile token early in the prompt forfeits the whole benefit. **Action**: pin `OLLAMA_NUM_PARALLEL=1`, enforce prompt ordering in `prompt_builder.py` (the rules in [11-AI-INTELLIGENCE.md](11-AI-INTELLIGENCE.md) §5), and Phase 0 spike #6 measures the actual cold-vs-warm TTFT delta so the win is a number, not folklore.
- [ ] **View Transitions API requires WebView2 ≥ Chromium 111.** Evergreen WebView2 (the default on Windows 11) is far past this; the risk only materializes if the app ever ships a *fixed-version* WebView2 runtime. **Action**: if fixed-version bundling is ever chosen in Phase 9, pin ≥111 and re-test tab transitions; also note React's `<ViewTransition>` component is still Canary-only — use the raw `document.startViewTransition()` API.

## Decisions made with explicit tradeoffs (not risks, but worth remembering why)

- **Live database unencrypted, only exports encrypted** — a deliberate performance/security tradeoff, not an oversight. If the threat model ever changes (e.g. a shared/less-trusted machine), revisit full-database encryption via SQLCipher.
- **Local model default superseded (historical)** — the original early-2026 choice was Mistral-7B-Instruct (quality-over-speed via partial offload). The July-2026 research round replaced it with `qwen3.5:4b` (fully VRAM-resident — better on *both* axes) + `gemma4:e4b` grammar alternate; see [11-AI-INTELLIGENCE.md](11-AI-INTELLIGENCE.md) §1. The lesson encoded into the architecture: model names are runtime settings, and the default gets re-evaluated against a bake-off, not inherited.
- **Multi-model routing partially arrived** — the original "small model for micro-fixes, big model for heavy work" idea landed differently: one fast VRAM-resident default (`qwen3.5:4b`) + an optional grammar specialist (`gemma4:e4b`) + an optional slower quality toggle (`qwen3.5:9b`), user-selected rather than auto-routed. Automatic per-task routing remains deferred.
- **Shared-scene continuity is Book-relative** — the same scene reused in two Books can legitimately get different continuity warnings depending on each Book's own outline order. This is by design (see [04-LLM-INTEGRATION.md](04-LLM-INTEGRATION.md)), not a bug, but it's easy to forget while debugging a "why did this flag disappear/appear" report.

## Name collision — resolved

A deeper prior-art search found two unrelated existing open-source projects already named "StoryForge"/"storyforge" (`91zgaoge/StoryForge`, a remarkably close conceptual match — Tauri+React+ReactFlow knowledge-graph canvas, local/cloud LLM, contradiction-flagging "Inspector" — and the unrelated `yuanbw2025/storyforge`). Rather than risk confusion with either, the project was renamed to **Quillnight** — chosen to reflect the author personally (tied to their birth moment, Feb 3 2003, 11:55 PM — five minutes before midnight — and the idea that stories/ideas often take shape at night) rather than a generic descriptive name. All docs and folder paths have been updated accordingly. Per the decision to study `91zgaoge/StoryForge`'s approach before finalizing later phases, see the license/architecture findings immediately below — its code turned out not to be reusable, but its design pattern is.

## License & prior-art code-reuse findings

A license check across the closest-match repos found for due diligence (not just naming) — the goal was to see if any could be legally adapted rather than building everything from scratch:

- **Verify the actual LICENSE file, never trust a README badge.** Three repos (`91zgaoge/StoryForge`, `yuanbw2025/storyforge`, `hooosberg/WitNote`) display an MIT or ISC license badge in their README with **no matching LICENSE file actually present in the repo** (confirmed via GitHub's own license API returning `null`). Under default copyright rules, that means all rights are reserved regardless of what the badge implies — none of the three are legally safe to copy code from. This is a general lesson worth keeping for any future "can I reuse this" check on this project, not just these three.
- **Safe to adapt code from (permissive license, verified)**: `lwhela12/AI-Screenwriting-Tool` (MIT), `Nigh/show-me-the-story` (MIT), `Proteus-Technologies-Private-Limited/OpenDraft` (MIT), `Mintplex-Labs/anything-llm` (MIT).
- **Not safe to copy code from for a closed/personal app (copyleft)**: `nodetool-ai/nodetool` and `ilrein/openwrite` (AGPL-3.0 — the network-use clause forces source disclosure on distribution/hosting), `chatboxai/chatbox` (GPL-3.0 — any distributed derivative must also be GPL'd). These remain fine as inspiration/ideas, just not as copied code.
- **`91zgaoge/StoryForge` specifically: inspiration-only, not forkable** — both because it has no valid license (above) and because, on inspection, its hardest-looking feature (the contradiction-checking "Inspector") turned out to be mostly prompt engineering (Markdown prompt templates asking the model to score several dimensions and return a fixed JSON schema) plus a thin typed struct to hold results — not dense, hard-won code worth copying even if the license allowed it. Its ReactFlow usage is also a knowledge-graph *visualizer*, not a scene/plot node canvas, so it doesn't map directly onto Quillnight's Node Canvas tab either.
- **What IS worth adopting (architecture/ideas aren't copyrightable)** from `91zgaoge/StoryForge`'s pattern: decouple fast drafting from an async, LLM-based audit step; have that audit call return a **fixed JSON schema with per-issue severity** (its shape: `{overall_score, dimensions:[{name, score, comment, issues}], critical_issues, suggestions}`) rather than freeform prose, then render the result as inline, severity-colored annotations rather than a flat list. This directly refines [03-DATA-MODEL.md](03-DATA-MODEL.md)'s `continuity_flags` table (now includes a `severity` column) and [04-LLM-INTEGRATION.md](04-LLM-INTEGRATION.md)'s continuity-check design.
- **From `Nigh/show-me-the-story` (MIT, safe to actually borrow code from if useful)**: an alternative continuity pipeline shape — diagnose → consistency audit → generate fix tickets → per-chapter auto-revision with a before/after diff — reinforces Quillnight's existing Accept/Reject-diff principle and is worth a look if the current continuity-check design needs a simpler fallback.
- **From `lwhela12/AI-Screenwriting-Tool` (MIT)**: a concrete "Beat Board" precedent (drag-and-drop, color-coded structure/flow lines) directly relevant to the Outline tab's beat-board view.

## Prior art worth remembering (from research, not to be re-derived later)

- **Tauri+Ollama integration lesson**: `vanvuongngo/ollama-tauri-qwik` found that streaming tokens via a plain synchronous JS `fetch` froze their UI on long generations, and moved streaming into a Rust `invoke`/`listen` IPC channel instead. Quillnight's design streams via the Python sidecar's SSE endpoint directly to React (never through Rust) using `fetch` + `ReadableStream`, which is architecturally different and shouldn't have the same freeze if implemented correctly (the streaming/cancellation design in [04-LLM-INTEGRATION.md](04-LLM-INTEGRATION.md) already uses `ReadableStream`, not a blocking fetch) — noted here as a specific thing to verify isn't happening once Phase 2 wires up real streaming, not just assumed fine by architectural difference alone.
- **`nodetool-ai/nodetool`** — a general node-based canvas wired to many LLM/image/audio models (not narrative-specific) — worth a look purely for node-canvas-plus-LLM interaction-pattern ideas (how a node's "run" action surfaces streaming/partial results in a graph UI).
- **`lwhela12/AI-Screenwriting-Tool`** — a drag-and-drop "Beat Board" (index-card style, not a true node graph) paired with a separate FastAPI service for context-aware suggestions — relevant as a beat-board UX reference for the Outline tab specifically.
- **`ilrein/openwrite`** — a web app (not desktop) with its own "Codex" system for characters/locations/lore/plot points plus BYOK AI assistance and a roadmapped "story canvas" — notable that it independently converged on the same "Codex" name/concept for the same purpose, a useful sanity check that this design direction is sound, not just internally-invented jargon.
- **`Nigh/show-me-the-story`** — a different architecture (single Go binary, outline → chapter-by-chapter loop with review/foreshadowing/fact-check passes) worth a glance for continuity-check *pipeline* structuring ideas, separate from Quillnight's node-canvas-first approach.
- **`Picrew/ConStory-Bench`** (the "Lost in Stories" paper's checker) mines contradictions across 5 categories/19 subtypes with cited textual evidence — this taxonomy is a directly reusable reference for structuring `continuity_checker.py`'s prompt/output categories, beyond just the general "it's a validated approach" note already in this doc.

- **No existing open-source tool combines a local LLM with story-bible contradiction detection** — this was confirmed by research, not assumed. The closest things are academic: "Lost in Stories" (arXiv 2603.05890, a 4-stage LLM-as-judge contradiction-detection pipeline across 5 categories/19 error subtypes — directly usable as a reference architecture for `continuity_checker.py`) and the "Finding Flawed Fictions" plot-hole benchmark (`kabirahuja2431/FlawedFictions`, arXiv 2504.11900), which is useful for later *testing* the continuity checker's accuracy. This means the continuity-checking feature is genuine differentiation, worth the engineering investment already planned for it, not a solved problem being reinvented.
- **`NousResearch/autonovel`** maintains a `canon.md` "hard facts" file and tracks **"propagation debts"** in `state.json` when established facts change — i.e., flagging every downstream entry that needs review after a canon edit. This is directly applicable to `codex_arc_states`: when a Codex entry's arc state changes, consider surfacing a "these N scenes may need review" list rather than only checking forward from a single scene. Worth revisiting during Phase 3/4 implementation, not required for the schema as currently designed.
- **`owlchester/kanka`** is the most feature-complete reference for entity modeling (characters/locations/orgs/families/timelines, all cross-linked via mentions) but is source-available under the Commons Clause — **do not reuse its code**, only its data-model ideas are fair game to learn from.
- **`wildwinter/screenplay-tools`** (already chosen for Fountain/FDX export) has a sibling project **`wildwinter/fountain-tools`** and a comparable alternative **`vilcans/screenplain`** (MIT) — if `screenplay-tools`' FDX fidelity (risk item above) doesn't hold up in the Phase 6 verification pass, `screenplain` is a documented fallback worth trying before hand-rolling an FDX writer.
- **`story-apps/starc`** ("Story Architect") imports a broader range of formats (FDX, docx, odt, Trelby, Celtx, Fountain) than Trelby alone — worth a look if the Final Draft tab's import needs ever expand beyond Quillnight's own canonical data.

## Author's own prior project — VIBE (owner-authorized reuse; selective)

> **UPDATE (2026-07-23):** The user confirmed they are the **sole owner** of `KarthikeyaSuppa/VIBE`
> and granted permission to **use it directly** (code + content, not just conventions). This
> supersedes the earlier "no LICENSE → all rights reserved → don't copy" caution below — that rule
> does not apply to a repo the user owns and authorizes. Reuse **selectively** (adapt the relevant
> vocab/field shapes/presets; do not blindly clone the whole project), and keep Quillnight's own
> structure/idioms. If VIBE code is pulled in verbatim, note its origin in a comment.

The author's earlier project **`KarthikeyaSuppa/VIBE`** ("Virtual Interactive Builder Of Experiences" — a RAG story generator; FastAPI + React/Vite/Tailwind + MongoDB) is a first-class source to mine — for both *conventions* and actual *code/content* — per the owner authorization above. Its data-model ideas and vocabularies:

- **Genre vocabulary + per-genre style presets** (the strongest reusable bit): genres `fantasy | scifi | romance | mystery | horror | adventure | general`, each with a preset `tone`, `pacing`, an ordinal `character_focus` / `setting_emphasis` (`balanced < moderate < high < very high`), and suggested `elements` tags. These map directly onto the **dropdowns / selects / sliders** the user requested for describing stories/scenes/characters.
- **Entity field shapes**: Character `{name, role, traits[], backstory, relationships[]}`; Scene `{type, location, description, participants[], actions}`; Story `{title, themes[], text, plotpoints, characters[]}`. These fold naturally into Quillnight's `codex_entries.custom_fields` JSON and scene metadata — no schema change required to *store* them.

**Open decision (resolve in Phase 1–3, not silently):** where structured metadata (genre, tone, pacing, focus scales) lives for the dropdown/slider UI — (a) keep it in existing flexible JSON (`books.front_matter` / `codex_entries.custom_fields`) driven by a shared option-vocabulary module that feeds the controls (no migration, reversible — **current lean**), or (b) add dedicated columns via a new Alembic revision if filtering/querying by them is later needed. The requested **dropdowns/selects/sliders** for scene/story/character attributes are a confirmed UX direction for the Codex (Phase 3) and node metadata (Phase 2), built from that shared vocabulary. VIBE's own UI is just a 3-field prompt/rating dialog — no existing widget to reuse.

## Open questions resolved during planning (kept here for traceability)

- **Script authoring UX** — resolved: structured screenplay elements (Scene Heading/Action/Character/Dialogue/Parenthetical/Transition) from the start in script-type Books, each individually Enhance-able, not freeform prose converted later.
- **Book-type conversion semantics** — resolved: AI-assisted transformation, human-in-the-loop (Accept/Reject like any Enhance call), and strictly non-destructive — original content (`description`) is preserved alongside any newly generated representation (`screenplay_elements`), never overwritten.
- **Workspace model** — resolved: hybrid. One shared live Story Library database for instant cross-Book reuse, plus automatic one-click encrypted `.quillproj` bundle export/import per Book for portability and backup.
- **Auto-suggest default** — resolved: off by default, with full debounce/cancel/keep-warm engineering built in regardless, so enabling it later is free.
- **Image pool scope** — resolved (creator's call, per explicit delegation): global reference pool across the whole library, but Book exports only bundle images actually linked to that specific Book.
- **AI provider modes** — resolved: Offline (local-only)/Online (Groq-only)/Hybrid (Groq-preferred with automatic local fallback), full design in [08-AI-PROVIDER-MODES.md](08-AI-PROVIDER-MODES.md). Auto-suggest is local-only in every mode, unconditionally — a deliberate exception, not an oversight.
- **Project name** — resolved: renamed from the working name "Story Forge" to **Quillnight** after finding two unrelated existing open-source "StoryForge" projects, one a very close match. The new name is personal rather than descriptive (see "Name collision — resolved" above).
- **Mascot** — resolved (user): yes, full firefly-with-quill companion. Ambient firefly ships v1.0; the Rive state-machine companion is v1.1 ([10-DESIGN-SYSTEM.md](10-DESIGN-SYSTEM.md) §6).
- **Voice input** — resolved (user): core feature. Local Parakeet (CPU) + Groq Whisper online, push-to-talk, raw audio kept ([12-VOICE-AND-SPEECH.md](12-VOICE-AND-SPEECH.md)). Clarified along the way: the user's locally-installed Larynx is a TTS engine (Piper's ancestor, same author) — relevant to read-aloud, not dictation.
- **Delight default** — resolved: **Playful**, chosen in the first-run Reading Comfort Wizard with a live preview; every element individually toggleable; `prefers-reduced-motion` overrides all ([10-DESIGN-SYSTEM.md](10-DESIGN-SYSTEM.md) §8).
- **Bionic Reading** — resolved: **rejected on evidence** (2,074-reader Readwise test + Acta Psychologica 2024 eye-tracking study: no speed/comprehension benefit; also trademarked). Recorded so it doesn't get re-proposed.
- **OpenDyslexic** — resolved: available as a font option (preference is legitimate) but **never the default** — studies show no speed/accuracy benefit. Default is Lexend + the onboarding font self-test, because measured individual fit beats any universal pick (Wallace 2022).
- **Background tint framing** — resolved: ship an adjustable warm background tint (evidence supports warm backgrounds for dyslexic readers) but make no "Irlen overlay" therapeutic claims — overlays-as-treatment are a debunked neuromyth.
- **Unaided self-refine loops** — resolved: rejected for small models (ACL 2024 evidence); refinement only against external verifiers (LanguageTool, string checks). [11-AI-INTELLIGENCE.md](11-AI-INTELLIGENCE.md) §7.
- **Thinking-mode + JSON schema in one call** — resolved: never combined (broken upstream: ollama#10929, llama.cpp#20345); two-pass reasoning→extraction instead. [11-AI-INTELLIGENCE.md](11-AI-INTELLIGENCE.md) §7.

## How to keep this document useful

- When a Phase 0 spike resolves an item above, replace its checkbox description with the actual measured result (e.g. "Measured 38 tok/s with `qwen3.5:4b` fully GPU-resident; prefix-cache warm TTFT 0.3s vs 4.1s cold") rather than just checking the box — the number itself is what later phases need, not just a confirmation that testing happened.
- Add new items here the moment a new unknown surfaces during implementation — don't let them live only in commit messages or your head.
