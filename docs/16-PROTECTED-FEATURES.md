# Protected Features (STRICT — do not weaken)

> ## Read this before editing anything in this file or the features it lists
>
> The features below are **primary, user-mandated behaviors**. A model (Claude or any
> other) working in this repo **must not remove, disable, hollow out, or quietly change**
> any of them. They were specified by the user directly and are load-bearing.
>
> **Enforcement rules:**
> 1. **Do not edit this file** — not the rules, not the list, not the wording — **unless
>    the user's message contains the literal keyword `spiderman`.** No refactor, cleanup,
>    "consistency" pass, or feature request implies permission to touch this file. If a
>    change seems to require editing it and the user did not say `spiderman`, stop and ask.
> 2. **Do not remove or weaken a listed feature** for any reason without the `spiderman`
>    keyword — even if it looks unused, redundant, or in the way of another change. Find a
>    way to make the new work coexist with it.
> 3. **Self-heal:** if you discover that a listed feature is **missing, broken, or
>    regressed**, restoring it takes priority — restore it (or flag it loudly to the user
>    if you can't) **before** continuing other work. A silently-dropped protected feature
>    is a defect, not an acceptable state.
> 4. Citations below are `file:symbol`/`file:line`. Line numbers drift as code changes —
>    trust the symbol/behavior, and re-verify the citation if it looks stale (do not treat
>    a drifted line number as "feature removed").
>
> This file is paired with a Hard rule in `CLAUDE.md` and `PROJECT-MAP.md §9` so it is

## Global invariant (already a Hard rule; restated because these features depend on it)

**AI never silently overwrites user text — every transform is Accept/Reject, Accept is the
sole writer, Reject/dismiss writes nothing.** Canonical seam: `enhance-diff.tsx`. Every
Enhance feature below inherits this and must keep inheriting it.

---

## P1. Every node type supports Title, Description, and Images

Scene, Plot Point, and Thought nodes all carry an editable **Title**, **Description**, and
**Images**, regardless of Book type.

- Title field — `components/canvas/node-editor.tsx` (`TitleField`, and the `Input` in
  `NodeEditorBody`).
- Description field — `components/canvas/node-editor.tsx` (`DescriptionField`), rendered
  **unconditionally** in `NodeEditorBody` (not gated on Book type), and `handleSave`
  **always** persists `description` (`node-editor.tsx:126` — do not restore the old
  `script ? {} : {description}` branch that skipped saving it for scripts).
- Images — `components/canvas/node-editor.tsx` (`SceneImagesSection`), rendered for all
  node/Book types.

## P2. Title Enhance (generate title from description)

A Sparkles Enhance control **fixed on the left of the Title field** generates a title
**from the description text** via LLM.

- `components/canvas/node-editor.tsx` (`TitleField`, ~line 355), `enhance.start({ mode:
  'title', text: description, … })` (~line 379).
- Backend mode — `apps/sidecar/app/services/prompt_builder.py`
  (`_TASK_INSTRUCTIONS["title"]`, `_TEMPERATURE_BY_MODE["title"]`, and `title` in the
  `Mode` literal); `apps/sidecar/app/models/schemas.py` (`EnhanceMode` includes `title`);
  `apps/desktop/src/queries/enhance.ts` (`EnhanceMode` includes `'title'`).
- **Accept writes the Title field only** (`setTitle(...)` + `acceptLog(logId, true)`) — it
  must **never** auto-PATCH the scene. Reject writes nothing (`acceptLog(logId, false)`).

## P3. Description Enhance — diff, Accept/Reject, Undo/Redo

- `components/canvas/node-editor.tsx` (`DescriptionField`) → `components/canvas/enhance-diff.tsx`
  shows the original→suggestion **diff**; the user picks which to keep (Accept/Reject).
- Accept is the sole writer (PATCH via `useUpdateScene`); after the write lands, an
  **Undo/Redo** affordance is surfaced via `showUndoToast(...)` in the mutation's
  `onSuccess` (reusing `queries/undo.ts`). Reject writes nothing.

## P4. Description version History (read-only, GitHub-style)

Every saved version of a scene's description is retained and viewable as a read-only,
copyable, version-by-version diff.

- `components/canvas/description-history.tsx` (`DescriptionHistoryButton`, ~line 118) →
  `useSceneRevisions` over the append-only `scene_revisions` table (`PHASE11.md`), rendered
  with the same `diffWordsWithSpace` coloring as `enhance-diff.tsx`.
- **Read-only:** no restore/rollback, no edit, no write path. Copy is clipboard-only
  (`navigator.clipboard.writeText`). Do not add a mutation here without `spiderman`.

## P5. Description box always visible & auto-resizing

The Description textarea is **always shown** (never collapsed/hidden) and **auto-resizes
vertically** to its content (grows and shrinks).

- `components/canvas/node-editor.tsx` (`DescriptionField`, the `el.style.height = 'auto'` →
  `scrollHeight` effect, ~line 515; `min-h-32 resize-none overflow-hidden`).

## P6. Add-elements list lives under the description; screenplay "Character" cue retained

- In `NodeEditorBody`, screenplay `ElementsEditor` renders **beneath** the Description
  (`node-editor.tsx`), for script Books. The **"Character" screenplay element type stays**
  (`ELEMENT_TYPE_LABELS.character`) — it is a Fountain/FDX cue line required by export
  (`apps/sidecar/app/services/export_fountain.py`) and is **not** the same thing as a Codex
  character (see `docs/17-CHARACTER-FLOW.md §5`). Do not remove or alias it.

## P7. Character chips under the description

Characters attached to a scene render as **circular chips** (image, else first ~3 letters),
**wrapping into rows**, with a **circular "Add character" button after the last chip**
(tooltip "Add character"). Clicking a chip opens that character's editor.

- `components/canvas/scene-characters.tsx` (`SceneCharactersSection`, ~line 37): circular
  `size-12` chips; dashed circular Add button (~line 95, aria-label "Add character to this
  scene"); click chip → `CodexEntryDialog`; **unlink (✕) removes only the scene link
  (`useUnlinkCodexFromScene`) — it must never delete the CodexEntry.** Add flow links an
  existing character (`useLinkCodexToScene`) or creates + links a new one (`useCreateCodex`).

## P8. New canvas node is created at the user's last click position

- `components/canvas/canvas-panel.tsx` (`handlePaneClick` stores `screenToFlowPosition`;
  `handleAddNode`/`handleAddNodeWithFocus` place the new node there, cascading slightly on
  repeated adds, falling back to the staggered offset only when no click is recorded).
- Lifecycle documented in `docs/15-ENTITY-LIFECYCLES.md` (Scene › Creation).

## P9. Characters-tab views: List + read-only D3-style relationship Map; NO Timeline view

- The Characters tab has **List** and **Map** views only — the Gantt "Timeline" view was
  removed and must not return (`components/codex/characters-panel.tsx`, `CharactersViewMode
  = 'list' | 'map'`).
- The **Map** is a **read-only** D3-style **circular node-link graph**
  (`components/codex/character-relationship-graph.tsx`): characters as circular nodes on a
  ring (avatar or 3-letter initials + name), relationships as curved "swoosh" edges, **one
  color per relationship type with a matching legend that doubles as a per-type filter**,
  hover-to-highlight (dim everything else + a pointer tooltip listing that character's
  relationships), and theme-token colors that read in both Day and Night. Clicking a node
  opens that character's editor. The map itself never mutates data — editing lives in the
  Relationships tab (P11).
- History: this superseded an earlier drag-to-connect editable map on 2026-08-02 (locked via
  `spiderman`). Do **not** reintroduce edge-drawing on the map without keeping P11 the writer.

## P10. Codex on the Canvas is a left sidebar drawer with circular chips

## P11. Character relationships are created/edited in the character editor (single writer)

- Each character's editor (`components/codex/codex-entry-dialog.tsx`, `RelationshipsSection`)
  is the **single writer path** for `codex_relationships` — pick another entry + a
  relationship type; create/delete via `useCreateRelationship` / `useDeleteRelationship`.
  As of 2026-08-09 this section lives in the **Details two-column rail** (it was a separate
  "Relationships" tab when first written — see P20); the single-writer invariant is what
  matters, not its tab location. The Map (P9) only visualizes these rows. Do not add a second
  relationship-editing surface (e.g. drag-to-connect on the map) without keeping this section
  the source of truth.

## P12. Canvas node action row: Duplicate (left), ⋯ (right), no inline Enhance

- Each canvas node's action row has **Duplicate on the left** and the **⋯ menu on the
  right**, and **no** inline Enhance button on the node itself
  (`components/canvas/nodes.tsx`). Enhancing happens inside the node editor's Title and

## P13. Help & Guide is a two-pane layout with per-topic diagrams

- `components/help/help-guide.tsx`: a wider dialog with a **left topic rail + right scrollable
  content pane** (not the old cramped horizontal tab strip), and a themed **SVG diagram** per
  topic (Canvas node/connections, Getting-Started flow, Codex link + relationship triad,
  Enhance Accept/Reject flow, Profiles, keycap shortcuts). Content scrolls inside a
  definite-height region (no overflow bleed). Keep it accessible (rail = real buttons,
  `aria-current`; diagrams `role="img"`).

## P14. Login persists across refresh (sessionStorage), not a full relaunch

- `stores/auth.ts` persists the session to **`sessionStorage`**: a page refresh/reload keeps
  the signed-in session; a full app close still returns to the `ProfileGate`. Do not revert to
  memory-only (loses refresh) or move to `localStorage` (would resume the last profile on
  relaunch — the safety posture the user chose against).

## P15. Four themes + a floating theme picker

- Four themes — **Day, Night, Sunset, Sunrise** — defined as `[data-theme='…']` token blocks
  in `index.css` (with `.dark` kept as the `dark:`-variant carrier for the dark-family themes).
  A **floating theme picker** (`components/theme-picker.tsx`) opens from a **bottom-left**
  button in the app-shell footer, showing the four themes as live preview tiles; selecting one
  applies instantly + persists (`theme_mode`). Settings' theme control stays in sync. All
  four themes' text pairs must remain **WCAG-AA** clean (contrast pass done 2026-08-02).

## P16. Glow on primary buttons — Playful + motion only

- The primary (`default`) `Button` variant shows an animated conic-gradient **hover glow**
  (`components/ui/button.tsx` `.qn-glow-btn` + `index.css`), gated to **both**
  `html[data-delight='playful']` **and** `@media (prefers-reduced-motion: no-preference)`.
  At Calm/Standard or under reduced-motion it's the plain button — no glow, no layout shift.
  Only the primary variant; keep it CSS-only.

## P17. Animated login background

- `components/auth/login-background.tsx`: a canvas **dot-grid** behind the `ProfileGate` with
  pointer-pull + spring-back + a staggered click-burst, hand-rolled RAF physics (**no GSAP /
  no paid plugin**), theme-token colored, `pointer-events: none` (never blocks the login).
  Under `prefers-reduced-motion: reduce` it renders a **static** grid (no listeners, no RAF).
  Sizing self-heals from the wrapper box (must not get stuck at 0×0 in embedded hosts).

## P18. Scroll-reveal highlight — chrome only, never manuscript/prose

- Reusable `components/ui/scroll-highlight.tsx` (`<ScrollHighlight hue? badge?>`): a `<mark>`
  highlight that wipes in on scroll (`animation-timeline: view()` with an `IntersectionObserver`
  fallback; `.qn-highlight` in `index.css`), theme-token colors that read in all four themes,
  and a **static** fully-highlighted state under `prefers-reduced-motion`.
- **Hard boundary:** only ever applied to **chrome / app-authored text** (Help guide, Timeline
  captions, merge-dialog labels — `help-guide.tsx`, `outline/timeline-view.tsx`,
  `canvas/merge-dialog.tsx`). It must **never** decorate the manuscript reader or raw user
  prose (scene descriptions / Draft) — the dyslexia-first "no decoration on reading surface"
  rule (P-global / docs/10 §8) overrides any request to highlight prose.

## P19. Slice-to-delete list-row removal animation

- `components/ui/slice-delete.tsx` (`useSliceDelete(onCommit, variant)`): a blade-sweep
  collapse (`'row'`) / scale-out (`'chip'`) removal animation (`.qn-slice-*` in `index.css`),
  **gated to `delight level === 'playful'` AND `motionOk`** — otherwise removal is instant
  (today's behavior, no regression). Wired to the list-row removals in `codex-panel.tsx`
  (chip delete), `node-editor.tsx` (`ElementRow` delete + `SceneImagesSection` image detach),
  and `scene-characters.tsx` (character-chip unlink).
- **Correctness invariant (do not weaken):** the caller's `onCommit` (the real
  delete/unlink/detach mutation) must fire **exactly once** across every path — instant,
  animation-end, and the `setTimeout` fallback — guarded by `committedRef`. The fallback timer
  is **deliberately not cleared on unmount** so a delete initiated then interrupted (drawer
  closed mid-animation) still commits rather than being silently swallowed. Never reintroduce
  unmount-cleanup on that timer.

## P22. Settings: two-pane layout + honest Local-vs-GroqCloud transparency

## P23. Notes tab — a cross-device scratchpad with two independent notes; local-first everywhere else

- A **Notes** nav item sits in the sidebar **between Search and Help** (`app-shell.tsx`,
  `/notes` → `routes/notes-screen.tsx`). It hosts **two independent notes**: a **LAN note**
  ("On your Wi-Fi", source of truth = local SQLite `notes` table, channel `'lan'`) and a
  **Cloud note** ("Anywhere", source of truth = Firestore). Editing one never touches the other.
- **Local-first boundary (do not weaken):** the Notes feature is the *only* part of Quillnight
  that touches the network. Books, Codex, canvas, scenes, drafts, and images must **never** be
  sent over LAN or cloud. Both notes carry only their own text + an LWW clock
  (`{content, updated_at, updated_by}` / `{content, updatedAt, updatedBy, schemaVersion}`).
- The sync layer is a pluggable seam — `lib/sync/adapter.ts` (`SyncAdapter`) with two impls
  (`lan-adapter.ts`, `cloud-adapter.ts`); the note store is last-write-wins by the ms clock.
  The mobile-app interface is frozen in `docs/18-NOTES-SYNC-CONTRACT.md` — keep the desktop
  side compatible with that contract (Firestore `notes/{uid}` shape + rules; LAN pairing
  handshake + `/pair` `/note` message shapes) so the separate Android app keeps working.

## P24. LAN Notes server: hard isolation + pairing security (never expose the rest of the app)

- The LAN note is served by a **separate, scoped ASGI app** (`apps/sidecar/app/lan/server.py`
  `build_lan_app()`) that mounts **only** `POST /pair` + `GET/PUT /note` — it must **never**
  import `create_app`/`app.api.*` or expose books/scenes/codex/any other data. The isolation
  test (`tests/test_lan_isolation.py`) asserts the route set is exactly `{/pair, /note}`; keep
  it passing.
- It binds `0.0.0.0` **only while the user toggles sharing on** (default off) and is torn down
  on stop + process shutdown. Security invariants (`app/lan/security.py`, `routes.py`): single-
  use 6-digit pairing code (~120s TTL, ≤5 attempts, `secrets.compare_digest`), 256-bit bearer
  `device_token` required on `/note`, unconditional `Origin`-header rejection on **both** routes
  (anti-DNS-rebinding), required `X-Quillnight-LAN` header, no CORS on the LAN app, nothing
  persisted to disk. Do not relax these or widen the LAN surface.
- **Robustness invariant:** a bind failure (port in use) must surface as a caught error (409),
  **never** crash the sidecar — `uvicorn`'s `SystemExit`-on-bind-fail is converted to a
  catchable failure (`_guarded_startup`/`_LanBindFailure`), and `start_lan_server` cancels +
  awaits + resets state on failure/timeout/cancellation so no orphaned listener wedges the port.
  Covered by `tests/test_lan_server_lifecycle.py`; do not remove that guard or those tests.

## P25. Cloud Notes network wall — one Firebase importer, publishable config only

- `lib/firebase.ts` is the **sole** module in the frontend that imports the Firebase SDK — the
  network wall. `cloud-adapter.ts` writes **only** `{content, updatedAt, updatedBy,
  schemaVersion}` to `notes/{uid}`. The Python sidecar makes **zero** cloud calls. Do not add a
  second Firebase importer or route cloud through the sidecar.
- The Firebase **web config is publishable** (not a secret) and lives in `app_settings`
  (`firebase_web_config`), **never** the keyring; no service-account secret is introduced.
  Firestore rules (`apps/desktop/firebase/firestore.rules`) scope `notes/{uid}` to its owner
  (`request.auth.uid == uid`). Google sign-in is opt-in; signed-out disables the cloud note but
  the LAN note still works. Do not weaken the rules or the config/secret split.
